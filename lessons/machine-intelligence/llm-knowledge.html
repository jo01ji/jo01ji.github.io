Machine intelligence · lesson 1

How LLMs hold knowledge

From the very basics (what an API call is, what a token is) up to pretraining, fine-tuning, prompting, retrieval and agents. The thread running through all of it is one question: where does the knowledge live, what shape is it in, and how does it reach the model at the moment it answers?

0 · The map

Three places knowledge can live

Everything in this lesson is a way of getting knowledge into one of three places. Keep this picture in mind; every later section points back to it.

Metallurgy linkWeights are like a microstructure: the whole processing history is in there, but implicitly, and you cannot read the furnace log back off it. The context window is like the mill certificate stapled to the sample: explicit, readable, and only as good as what someone chose to write on it.
1 · Basics

What an API is

An API (application programming interface) is a fixed way for one program to ask another program to do something. For an LLM, the "other program" runs on the provider's servers. Your code sends a request over the internet (a block of text in a format called JSON), and gets back a response (more JSON). The chat window you use is just a friendly program sending these requests for you.

Here is a complete call in Python using Anthropic's SDK (a library that builds the JSON for you). Line by line:

import anthropic                       # load the library (install once: pip install anthropic)
client = anthropic.Anthropic()          # reads your secret key from the ANTHROPIC_API_KEY variable

reply = client.messages.create(         # send one request
    model="claude-opus-5-5",            # which model to run
    max_tokens=500,                     # stop after at most 500 output tokens
    system="You are a physical metallurgist.",   # standing instructions
    messages=[                          # the conversation, oldest first
        {"role": "user", "content": "What is Widmanstätten ferrite?"}
    ],
)
print(reply.content[0].text)            # the model's answer
print(reply.usage)                      # input_tokens and output_tokens: what you pay for
The most important fact on this pageThe model is stateless. It remembers nothing between calls. A "conversation" works because your program re-sends the whole history every time. Any "memory" an app seems to have is the app putting text back into the context window.
Words you will meetsystem = standing instructions. messages = alternating user and assistant turns. max_tokens = output budget. temperature = randomness (section 3). tools = functions the model may ask you to run (section 12).
2 · Basics

Tokens: the unit the model actually reads

The model never sees letters or words. Text is first cut into tokens: common chunks of characters from a fixed vocabulary of tens of thousands to a few hundred thousand entries, built by an algorithm such as byte-pair encoding (BPE). Each token becomes an integer ID. Common words are one token; rare words, numbers, chemical formulas and non-English text are split into several. As a rough rule for English, one token is about three quarters of a word.

Tokens matter for three practical reasons: you pay per token in and out; the context window (section 8) is measured in tokens; and anything the model must reason over, from a paper to a knowledge graph, has to be turned into tokens first. That last point comes back in section 10.

3 · How a prompt becomes an answer

One token at a time

An LLM does one thing: given all the tokens so far, it outputs a probability for every token in its vocabulary being next. One token is picked, appended, and the whole thing runs again. A 500-token answer is 500 passes. This loop is called autoregressive generation.

Try it: temperature

The model's raw scores (logits, z) are turned into probabilities by the softmax, pi = exp(zi/T) / Σ exp(zj/T). Temperature T sharpens or flattens the distribution. The softmax maths below is exact; the six logits are invented for illustration.

Allotriomorphic ferrite nucleates at prior austenite ___
Low T: almost always the top token. High T: more variety, more nonsense.
Why this matters for knowledgeThe model never "looks up" a fact. A fact the model "knows" is just a continuation it assigns high probability. A wrong fact stated fluently (a hallucination) is a high-probability continuation that happens to be false. Nothing inside marks which continuations are sourced.
4 · Inside the model

Embeddings, attention and layers

Modern LLMs are transformers (Vaswani et al., 2017). Three ideas cover most of what happens in one forward pass.

Embeddings. Each token ID is turned into a long vector of numbers. Training moves related meanings close together, so distance in this space means something. RAG (section 9) uses the same trick to find relevant documents.

Attention. Each token looks back at every earlier token and decides how much each one matters to it. Here "it" attends mostly to "plate". This is how context changes meaning, and how text you put in the prompt gets used.

Where facts sitProbing studies suggest much factual recall runs through the feed-forward (MLP) layers, which behave a bit like a key-value memory (Geva et al., 2021; Meng et al., 2022 located and edited single facts this way). But a fact is smeared over many weights and entangled with others. You cannot point to "the weight that stores the eutectoid temperature".
5 · Knowledge into the weights

Pretraining a foundation model

Pretraining starts from random weights and trains on trillions of tokens of text (web pages, books, code, papers) with one objective: predict the next token. Every wrong guess nudges billions of weights slightly (gradient descent). Run this for weeks on thousands of GPUs and the model that comes out is a foundation model or base model.

ScaleKaplan et al. (2020) and Hoffmann et al. (2022, "Chinchilla") showed loss falls predictably as you add parameters, data and compute together. That is why models are huge, and why almost nobody outside a few labs pretrains a frontier model. You will use a pretrained one.
Knowledge cutoffThe model knows nothing after the date its training data was collected, and it is uneven before that: a 2023 debate in a niche journal may be barely represented. Petroni et al. (2019) first measured how much factual knowledge a model holds by "fill in the blank" probes.
Metallurgy linkPretraining is lossy compression, a bit like a CALPHAD assessment: thousands of measurements are fitted into a compact parameter set that generalises well, but you cannot recover which experiment pinned which parameter, and sparse regions of composition space are extrapolations.
6 · Changing the weights after pretraining

Fine-tuning and post-training

A base model just continues text; it is not yet a helpful assistant. Post-training reshapes it with much smaller, curated datasets. The same tools are what people mean by fine-tuning a model for their own task.

StageDataWhat changes
Supervised fine-tuning (SFT)Thousands of example prompt → ideal answer pairsFormat, tone, following instructions, domain style
Preference tuning (RLHF, RLAIF, DPO)Pairs of answers ranked better/worse by people or by a model against written principlesHelpfulness, honesty, refusing harm, judgement (Ouyang et al., 2022)
Reinforcement learning on tasksProblems with checkable answers (maths, code)Longer step-by-step reasoning; the basis of "reasoning" models
Your own fine-tuneYour labelled examples, often a few hundred to a few thousandNarrow behaviour: a fixed output schema, a classification, a house style

LoRA (Hu et al., 2021). Instead of updating a huge matrix W, train two thin matrices whose product is a small correction. Often well under 1% of the parameters, so a fine-tune fits on one GPU.

Is fine-tuning a good way to add facts?

Usually not on its own. Ovadia et al. (2024) compared unsupervised fine-tuning with retrieval for injecting new facts and found retrieval consistently better. Gekhman et al. (2024) found that fine-tuning on facts the model did not already know is learned slowly and increases its tendency to hallucinate. Fine-tuning is good at teaching how to behave; it is weak at teaching what is true, and it erases provenance just as pretraining does.

Metallurgy linkFine-tuning is tempering, not re-melting: a small, cheap treatment that changes properties of the existing structure. It cannot add an alloying element the heat never had.
7 · Steering without training

Prompt engineering

If the weights are fixed, the only lever left is the text you send. Prompt engineering is the craft of writing that text so the model's most probable continuation is the one you want. It works because of in-context learning: Brown et al. (2020) showed large models can pick up a task from a few examples in the prompt, with no weight change at all.

TechniqueWhat you doWhy it helps
Role / system promptSay who the model is and who the reader isShifts vocabulary and level of detail
Clear task + constraintsState the goal, the limits, what to do when unsureRemoves guessing about intent
Few-shot examplesShow 2–5 worked input → output pairsFixes format and the decision boundary
Delimiters / tagsWrap documents and instructions in labelled blocksModel can tell instructions from data
Chain of thoughtAsk for reasoning before the answerGives the model tokens to "think" in (Wei et al., 2022). Reasoning models now do this internally.
Structured outputAsk for JSON matching a schemaMachine-readable, easy to score
Grounding instruction"Answer only from the documents and cite them"Pushes the model toward in-context knowledge over its weights
DecompositionSplit a big task into a chain of smaller callsEach call is simpler and checkable
The key insightA prompt is already a knowledge representation. Ordering, labels, which details you include and which you leave out all change what the model attends to. Every method in sections 9 and 10 is, in the end, a disciplined way of building a prompt.
8 · Working memory

The context window

The context window is the maximum number of tokens the model can take in one call (input plus output). Current frontier models handle hundreds of thousands of tokens, some up to around a million. Everything the model can use at answer time, apart from its weights, must fit here.

Shape of the "lost in the middle" result (Liu et al., 2024): models used information at the start and end of a long context better than in the middle. Schematic curve; newer models are better but position still matters.

Why not just paste everything?

  • Cost and speed grow with every token.
  • Distraction: irrelevant text lowers accuracy (Shi et al., 2023).
  • Position effects: see the curve.
  • No built-in structure: 40 pasted papers are one long string. Which claim came from which paper, and which is newer, is only recoverable if you wrote it into the text.

So the real question becomes: which knowledge to put in, and in what form. That is retrieval (section 9) and representation (section 10).

9 · Fetching knowledge at answer time

Retrieval-augmented generation (RAG)

RAG (Lewis et al., 2020) splits the job in two. A retriever finds the few passages most relevant to the question; the LLM then answers with those passages in its context. The model stays fixed; you change what it reads.

Knowledge conflictsWhen retrieved passages disagree with each other or with the model's weights, behaviour is hard to predict: models may side with the more frequent claim, the more fluent one, or their own prior. Variants of RAG that deliberately retrieve and present multiple positions are one response.

10 · The centre of the lesson

  
Knowledge representation: what shape the knowledge takes

  
Knowledge representation is the choice of structure used to store knowledge and hand it to a reasoner. For an LLM there is one hard constraint: whatever the structure, it arrives as tokens (or as weights). A knowledge graph, a table and a timeline all become text in the context window. So the representation decides two things: what retrieval can select on, and what is explicit in the text the model reads, rather than left for it to infer.

Three questions to ask of any representation1. What does it make explicit that plain text leaves implicit? 2. Can retrieval select on that structure (by source, date, stance), or only on word similarity? 3. Once serialised into tokens, does the model actually use the extra structure, or treat it as more prose?

    
Separating the variables"Representation" and "retrieval" are different knobs. Two systems can retrieve the same passages and present them differently, or present the same structure but retrieve different items. Clean comparisons hold one fixed while varying the other.

  







  
11 · Three architectures compared

  
Implicit, retrieved, structured: is it really one spectrum?

  
It is natural to line the three up as implicit → explicit, and as a first ordering that is useful. But it hides something important, and the thing it hides is exactly where the interesting design decisions are. "Implicit versus explicit" is really at least four independent axes, and the three architectures sit in different places on each.


  

    
    
The same three systems, placed on four axes that do not move together. A knowledge graph is far right on formality and addressability, but on the fourth axis (does the model reason over the structure itself?) it collapses back to the left along with everything else, because the triples are serialised into tokens before the model sees them.

  


  
The thing the one-spectrum picture hides

  
Whatever structure you build, the transformer at the end receives a string of tokens. A knowledge graph is not explicit to the model. It is explicit to the retrieval and checking machinery that runs before and after the model. That is where the value is, and it is real, but it is worth being precise about it.

  

    
  

  
Put another wayStructure buys you three things, all of them outside the model: selection (you can ask for claims by source, date or stance, not just by word similarity), aggregation (you can count, group and traverse, which a pile of passages cannot do), and audit (every token in the prompt traces back to something). It does not give the model a different way of thinking. The reasoning is soft, probabilistic and in the weights, whatever you feed it.

Is explicit structure good for science?

  
For some of what science needs, yes, and decisively so. Structured knowledge is the only one of the three that supports the operations a literature review actually consists of: count how many independent groups report an effect, group them by method, sort by date, detect that two measurements of the same quantity disagree, slice by what was believed before a given paper, and trace a number back to the sample it came off. A pile of retrieved passages cannot do any of those, because the retriever only ever hands over the k passages that look most like your question.

  
There is a second reason, specific to physical science: structured knowledge is computable. A triple carrying a value, a unit and a condition can be fed to a solver, checked for dimensional consistency, or compared against a model. A sentence cannot.

  

    
    
The cost of formalising. The bare triple is clean, queryable and wrong in a way that matters: it has dropped the conditions, the strength of the claim and who is making it. A schema rich enough to keep them is most of the work in building a scientific knowledge base.

  

  
Where formal structure fights scienceScientific claims are conditional ("at low undercooling"), hedged ("appears to be", "consistent with"), contested, and revised. A schema is a commitment, made in advance, about what kinds of things can be said. Anything the schema has no slot for silently disappears, and in an open, moving field that is a lot. This is the open-world problem, and it is why formal scientific knowledge representation keeps reinventing qualifiers: nanopublications, micropublications, PROV, and the assertion/provenance split all exist to put the hedging back in.


  
Does explicit structure lack contextual understanding?

  
This is worth stating carefully, because the obvious answer is slightly off. A knowledge graph does not understand anything, but neither does a passage of text. Neither is a reasoner. The understanding, such as it is, happens in the model in all three cases, and the model is the same model.

  
So the real question is not whether the representation understands. It is what the representation throws away before the model gets to read it. And a graph throws away a great deal: the reasons, the "although" and "because", the argument the author was making, the way a result was qualified three sentences later. Prose carries all of that for free, which is why a retrieved paragraph often beats a set of triples extracted from the same paragraph, even on questions the triples were built to answer.

  

    
  

  
Which points at the design that most serious systems converge on. Use the structure for what structure is good at, which is finding and organising, and then hand the model the original prose for the things it chose. The graph decides what is relevant and in what relation; the passages carry the nuance. GraphRAG (Edge et al., 2024) works this way: it builds a graph and community summaries over a corpus, but the nodes point back at the source text.

  
Metallurgy link: a fourth modeThere is one more source of knowledge that is neither remembered nor retrieved: computed. When you call Thermo-Calc, the answer does not exist anywhere until you ask. A CALPHAD database is an explicit, versioned, auditable knowledge representation whose contents are Gibbs energy functions rather than sentences, and the way a model uses it is as a tool (section 12), not as a document. For quantitative questions this is usually better than any of the three above: the LLM decides what to calculate, and the calculation is right for reasons that have nothing to do with the LLM.

  
A rough ruleUse the weights for language, framing and common ground. Use retrieval when the answer is written down somewhere and you need the nuance of how it was written. Use structure when the question is about the shape of the literature rather than its content: how many, who, when, which disagree, what changed. Use a tool when the answer can be calculated. Most real questions want more than one.







  
12 · Letting the model act

  
Agent architecture

  
An agent is an LLM in a loop with tools. You describe functions the model may call (name, description, input schema). Instead of answering, the model can reply "call search_papers with these arguments". Your program runs the function and sends the result back as a new message. The loop repeats until the model answers. ReAct (Yao et al., 2023) named this reason-then-act pattern.

  

    

      
    

    

      
The parts of an agent

      
    
        
  • Model: the fixed LLM doing the reasoning.
    • 
        
  • Tools: functions with schemas. The model never runs code itself; it only asks.
    • 
        
  • Loop / harness: the program that runs tools and feeds results back.
    • 
        
  • Planning: writing a plan or to-do list into the context and updating it.
    • 
        
  • Memory: files or databases the agent writes and re-reads across sessions.
    • 
        
  • Multi-agent: one model hands sub-tasks to others with their own contexts.
    • 
      

      
Protocols such as MCP standardise how tools are described so one agent can plug into many services. Retrieval as a tool, where the model decides when and what to search, is often called agentic RAG.

    

  

  
Step through a trace

  

    

    

  

  
Agents and knowledgeAn agent does not change how knowledge is represented; tool results still land in the context as tokens. What it changes is who chooses the knowledge: the model itself decides what to look up next, based on what it has read so far.







  
13 · Knowing whether it worked

  
How people measure knowledge delivery

  
Methods in this field are compared empirically. A few habits separate convincing comparisons from anecdotes.

  

    

      
Controls

      
    
        
  • Fix the model (same version, same temperature) so differences come from the knowledge, not the model.
    • 
        
  • Fix the sources so one system is not simply reading more.
    • 
        
  • Match the token budget; more context can help or hurt on its own.
    • 
        
  • Ablate: remove one ingredient at a time to see which one carries the effect.
    • 
        
  • Closed-book baseline: no retrieval, to see what the weights already know.
    • 
      

    

    

      
Pitfalls

      
    
        
  • Contamination: the answers may already be in the pretraining data.
    • 
        
  • LLM-as-judge bias: a model grading answers may prefer longer or more confident ones (Zheng et al., 2023).
    • 
        
  • Variance: run repeats; small differences are often noise.
    • 
        
  • Metric choice: accuracy, faithfulness to sources, citation correctness and calibration can move in different directions.
